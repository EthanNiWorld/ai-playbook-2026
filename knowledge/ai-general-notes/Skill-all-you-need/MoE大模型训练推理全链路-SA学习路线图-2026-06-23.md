## 一、训练全链路：MoE 模型从 0 到 1（15 步）

### 预训练阶段

```
[1] 数据收集 → [2] 数据清洗 → [3] 数据配比 → [4] 分词器训练
    多源并行抓取    分shard并行去重   代码20%/网页60%    BPE/SentencePiece
                                    数学10%/书籍5%      词汇量50K-256K

[5] 架构设计 → [6] 小规模验证 → [7] 大规模预训练（核心）
    Dense vs MoE    1/100规模         DP × TP × PP × EP 四维并行
    专家数/top-k    多组超参并行      all-to-all 通信 · 负载均衡
    路由策略/辅助loss  Scaling Law外推   10T-20T tokens · 数周至数月
```

> **MoE 特有挑战：** EP（Expert Parallelism）将不同专家分布到不同 GPU，每个 token 只去 top-k 专家，需要 all-to-all 通信。Dense 层和 MoE 层在同一集群上混合使用不同并行策略。负载不均衡（热门 vs 冷门专家）需要辅助 loss 强制均衡。

### 后训练阶段

```
[8] SFT → [9] RM训练 → [10] RL对齐（核心） → [11] 能力专项
    监督微调   可跳过      三选一：              代码RL/数学RL/
    1万~100万条           PPO/GRPO/DPO          Agent RL（可并行）
                          GLM-5.2: Critic-Based PPO + Anti-Hack
                          DeepSeek-R1: GRPO

[12] 基准评估 → [13] 安全测试 → [14] 推理优化 → [15] 部署上线
    MMLU/SWE-bench  红队攻击        量化/投机解码    vLLM/SGLang
    HumanEval/AIME  越狱/偏见       KV-cache压缩    K8s/灰度发布
    全benchmark并行  隐私泄露        Continuous Batching
```

> **串行依赖：** 数据 → 清洗 → 配比 → 分词器 → 预训练 → SFT → RL → 部署（不可跳过）。  
> **可并行：** 数据收集（多源）、数据清洗（分 shard）、架构搜索（多组超参）、预训练内部（4D 并行）、RL 采样（多 rollout worker）、能力专项（代码/数学/Agent 分开）、基准评估（全 benchmark 同时跑）。

### PPO vs GRPO vs DPO — 为什么 GLM-5.2 选择 PPO？

长程编程任务（如"花 10 小时优化 CUDA kernel"）的轨迹太长，必须压缩（compaction）。一条超长轨迹变成 N 条子轨迹，不同 rollout 的 N 不同。GRPO 的组内标准化假设"每个 rollout 产生 1 个 reward"彻底崩塌。PPO 的 Critic 可以独立估计每个子轨迹的 token 级 advantage，长度无关。

| 维度 | PPO | GRPO | DPO |
|------|-----|------|-----|
| **本质** | 强化学习（Actor-Critic） | 强化学习（无 Critic） | 非 RL（直接偏好优化） |
| **Advantage 来源** | Critic 网络学习 V(s) | G 个 rollout 组内标准化 | 不需要 |
| **额外模型** | 需要 Critic | 不需要 | 不需要 |
| **在线采样** | ✅ | ✅ | ❌ |
| **适用场景** | 长程复杂探索（编程 Agent） | 有明确 reward（数学推理） | 偏好对齐（安全/有用） |
| **代表模型** | GLM-5.2 | DeepSeek-R1 | Llama 3 |

## 二、推理全链路：从模型部署到用户响应

> **训练 vs 推理：** 训练的目标是**吞吐量最大化**（离线批处理），推理的目标是**延迟最小化 + 质量最优化**（在线实时服务）。两条完全不同的技术栈。

### 阶段 0：模型部署

```
[1] 模型导出 → [2] 量化压缩 → [3] 引擎加载 → [4] 服务启动
    PyTorch→推理格式  INT8/INT4/FP8    vLLM/SGLang      加载权重到GPU
    HuggingFace/      AWQ/GPTQ         TensorRT-LLM     预分配KVCache
    ModelScope/GGUF   显存降低2-4×     llama.cpp        K8s/负载均衡
```

### 阶段 1：单次请求处理

```
用户输入 → [5] 分词 → [6] Prefill → [7] Decode → [8] 输出
"写一个快排"  Tokenizer  一次算完所有   逐个生成      去分词
                       输入token      输出token      返回文本
                       生成KVCache    复用KVCache
                       ~10ms          ~500ms(占98%)
                       ⚡计算密集      🐌内存密集
```

### Prefill vs Decode：推理最核心的矛盾

| | Prefill（预填充） | Decode（解码） |
|---|---|---|
| 处理方式 | 一次处理所有输入 token | 一次只生成 1 个 token |
| GPU 利用率 | 高（并行计算） | 低（大部分时间等显存） |
| 延迟 | O(1) 次前向 | O(N) 次前向 |
| 瓶颈 | 计算密集（矩阵乘法） | 内存密集（读 KV Cache） |

> **瓶颈：** 假设输入 1000 tokens + 输出 500 tokens，总延迟 ~510ms，Decode 占 98%。

### 推理的瓶颈全部在 Decode 阶段 → 对应的优化技术

| 瓶颈 | 技术 | 代表方案 | 原理 |
|------|------|----------|------|
| KV Cache 显存爆炸 | KV Cache 压缩 | MLA（DeepSeek）/ IndexShare（GLM）/ MSA（MiniMax） | 低秩压缩 / 稀疏注意力 / blockwise 稀疏 |
| | KV Cache 分级 | LayerSplit（GLM） | GPU→CPU→磁盘三级管理 |
| | PagedAttention | vLLM | 分页管理，不连续分配 |
| Decode 太慢 | 投机解码 | MTP（DeepSeek/GLM） | 一次预测多个 token |
| | Continuous Batching | vLLM | 多请求拼在一起算 |
| GPU 利用率低 | Prefill-Decode 分离 | DistServe/Mooncake | 不同 GPU 分工 |
| 显存不够 | 量化 | INT8/INT4/FP8 | 降低权重精度 |

### MoE 推理的特殊性

| ✅ 优势 | ⚠️ 挑战 |
|---------|---------|
| 每个 token 只激活 top-k 专家（如 8/256） | 专家分布在不同 GPU → all-to-all 通信 |
| 671B 总量 → 实际激活 ~37B | 热门专家 GPU 过载 |
| 推理速度远快于同规模 Dense 模型 | 推理时负载均衡比训练时更难 |

## 三、推理时计算（Reasoning）：用更多算力换更好质量

> **推理优化两大方向：**
> - **方向 A：系统优化** — 让每一步计算更快、更省（KV Cache 压缩、量化、投机解码、Continuous Batching）。衡量：TTFT、TPOT、吞吐量。
> - **方向 B：推理时计算（Reasoning）** — 花更多算力生成更好的答案（Chain-of-Thought、Best-of-N、Verifier、Tree Search）。衡量：准确率、HLE 分数、AIME 分数。

### 推理时计算的演进路线

```
2023         简单 CoT（"Let's think step by step"）
              │
2024 Q3      OpenAI o1 隐藏式推理链（黑盒）
              │
2025.01      DeepSeek-R1 公开推理链（白盒，GRPO）
2025.01      MiniMax-M1 Lightning Attention 支撑超长推理链
              │
2025.04      Qwen3 Thinking Mode 开关（用户可控）
              │
2026.06      GLM-5.2 Effort Level 分级（High/Max）
```

### 各家 Reasoning 方案对比

| | DeepSeek-R1 | Qwen3 | GLM-5.2 | MiniMax-M1 |
|---|---|---|---|---|
| **推理模式** | 始终思考 | 开关式（Thinking/Non-thinking） | 多级（High/Max effort） | 始终思考 |
| **推理链可见** | ✅ 可见 | ✅ Thinking 模式可见 | 取决于 effort | ✅ 可见 |
| **训练方法** | GRPO | 混合 RL | Critic-Based PPO | 未公开 |
| **核心创新** | 冷启动数据 + GRPO | 同一模型双模式 | effort level 控制 | 4M 上下文支撑超长推理 |

> 注：MiniMax M3 的推理时计算方案尚未公开，上表为 MiniMax-M1 的数据。

### 推理时计算的核心公式

```
答案质量 = f(推理时算力)

├─ Chain-of-Thought：生成更多 token → 更多思考 → 更好的答案
├─ Best-of-N：生成 N 个答案 → 选最好的 → 质量 ↑，成本 ↑ N 倍
├─ Verifier：生成答案 → 验证 → 不对就重试 → 质量 ↑，成本 ↑
└─ Tree Search：分支探索 → 评估 → 选择最优路径 → 质量 ↑↑，成本 ↑↑↑

本质：用推理时的算力换取训练时无法达到的质量。
```

## 四、四家推理优化技术全景对比

| 技术维度 | DeepSeek | Qwen | MiniMax（M3, 2026.06） | GLM（智谱） |
|----------|----------|------|---------|------------|
| **KV Cache 压缩** | **MLA**（多头潜在注意力）低秩联合压缩 K/V，~15× 压缩（93.3% reduction） | **GQA**（分组查询注意力）减少 KV 头数，~4× 压缩 | **MSA**（MiniMax Sparse Attention）blockwise 稀疏注意力，GQA + Index Branch，1/20 per-token compute | **IndexShare** 稀疏注意力索引器共享，FLOPs 降低 2.9× |
| **投机解码** | **MTP**（多 Token 预测） | 未公开 | 未公开 | **MTP + KVShare** 接受长度 +20% |
| **长上下文** | 128K-1M（MLA 支撑） | 128K-1M（YaRN 扩展） | **1M**（MSA，9× Prefill / 15× Decode 加速） | **1M 实测可用**（IndexShare + 编码Agent专项训练） |
| **推理时计算** | GRPO 训练推理链（R1） | **Thinking Mode 开关** | 未公开 | **Effort Level 分级** |
| **MoE 推理** | 细粒度专家 + 共享专家 | Dense 为主 | MoE | MoE |
| **推理引擎** | vLLM/SGLang 自研优化 | vLLM/SGLang | 自研 | 自研 LayerSplit |
| **核心论文** | DeepSeek-V2 (2024.05) | Qwen2.5 (2024.09) | MSA (2026.06) | IndexShare (2026.03) |

### KV Cache 压缩：三条路线竞合

| 路线 | 代表 | 原理 |
|------|------|------|
| **路线 A：低秩压缩** | DeepSeek MLA | 把 K/V 投影到低维空间 → 存潜在向量 → 计算时解压 |
| **路线 B：线性注意力** | MiniMax-01 Lightning（上一代） | 把 O(n²) 变成 O(n) → 不需要 KV Cache |
| **路线 C：稀疏注意力** | GLM IndexShare、MiniMax M3 MSA | 只关注最相关的 token → 减少计算量。IndexShare 共享索引器，MSA 用 GQA+Index Branch 做 blockwise Top-k |

> **趋势判断：** 路线 B（线性注意力）在 MiniMax-01 上达到 4M 推理外推，但 M3 转向了路线 C（MSA 稀疏注意力），说明稀疏注意力在 2026 年成为主流方向。三条路线未来可能融合（MLA + 稀疏 + 线性）。

### 🔑 面试必问三点

1. **PPO vs GRPO vs DPO 的区别和适用场景**（为什么 GLM-5.2 选 PPO？为什么 DeepSeek-R1 选 GRPO？）
2. **MoE 的 4D 并行**（DP × TP × PP × EP）中 EP 的工作原理和 all-to-all 通信挑战

### ⚠️ 高频陷阱

- **「DPO 是 RL 算法」**— ❌ 错！DPO 本质是分类任务（MLE），不是 RL。
- **「GRPO 比 PPO 好」**— ❌ 不一定！长程编程 Agent 场景下因轨迹压缩导致组内比较失效。
- **「推理只关心速度」**— ❌ 不全面！推理时计算（Reasoning）用更多算力换更好质量，与系统优化同等重要。

### 🚀 一句话总结

**RL 对齐 + MoE 训练 + 推理系统优化 + 推理时计算** 是 SA 必须能讲透的四大硬核知识。预训练决定了模型的**知识上限**，后训练决定了模型的**行为下限**，推理系统优化决定了**服务成本**，推理时计算决定了**答案质量**。四者缺一不可。

01 / REQUEST LIFECYCLE

一次请求到底经历了什么？

LLM 服务不是“把请求交给 GPU 然后等结果”。它是一条包含排队、调度、显存状态管理和流式输出的流水线。TTFT 主要发生在首个 token 之前，TPOT 则描述后续生成节奏。

PREFILL · 首 token 前

一次前向，处理 S 个输入 token

输入位置可以大规模并行，权重被一批 token 复用，同时生成 Prompt 的 KV Cache。输入越长，注意力二次项越不能忽略。

直接影响：TTFT、输入 token 吞吐、长 Prompt 成本。

DECODE · 首 token 后

每步依赖上一 token，自回归生成

每个活跃序列通常每步推进一个 token，并读取已有 KV。权重在低 batch 下难以充分复用，kernel launch 与调度开销也更明显。

直接影响：TPOT、输出 tok/s、长输出成本。

真实引擎不是两个孤立阶段。 vLLM 的 continuous batching 会在同一调度循环中混合 prefill 与 decode。长 Prompt 的 prefill 可能阻塞其他请求的 decode，因此“提高 prefill batch”并不必然改善整体 SLA。
02 / FIRST PRINCIPLES

每个 token 都在消耗两种资源

一类资源是计算：矩阵乘法和注意力；另一类是数据搬运：从显存读取权重、KV Cache 和激活。哪一类先耗尽，哪一类就是当前瓶颈。

Rtoken ≤ min(Ceff / Ftoken, Beff / Dtoken)R：token/s；C：有效算力 FLOP/s；F：每 token 计算量；B：有效显存带宽 byte/s；D：每 token 显存读取量。

用算术强度判断在哪一侧

AI = Ftoken / Dtoken　　AI* = C / BAI < AI*：偏显存带宽瓶颈；AI > AI*：偏算力瓶颈。实际系统还要叠加 KV、通信、kernel 与调度开销。

为什么低并发 decode 偏访存？

每步计算量约为 2P，却可能重新读取接近整份权重。batch=1 时权重无法跨序列摊薄，算术强度很低。

为什么长 prefill 偏计算？

S 个输入 token 共享同一份权重读取，权重流量被摊薄为约 W/S；矩阵规模更大，也更容易喂饱 Tensor Core。

为什么高并发 decode 会转向？

N 个序列摊薄权重读取，但每序列 KV 仍要读取。增大 N 可提高吞吐，最终撞上算力、KV 带宽或调度上限。

显存容量与显存带宽不是一回事。 容量决定“能否装下权重、KV 和运行时”；带宽决定“每秒能读多少字节”。PCIe 带宽则主要影响模型加载、CPU↔GPU 与多卡 TP 通信，不能冒充显存带宽。
03 / CORE FORMULAS

从参数量推导理论吞吐

以下是用于理解数量级的简化模型。对 Dense LLM，线性层每 token 前向计算量约为 2P；注意力、视觉编码器、KV、采样和通信需另行计入。

3.1 权重与容量

W ≈ P × bytes/param + scales/metadata
MVRAM ≥ W + MKV + Mactivation + Mruntime27B BF16 权重约 54 GB；FP8 理想权重约 27 GB，实际还需 scale、元数据与其他参数。

3.2 Prefill：输入吞吐与 TTFT

Rprefill,compute ≈ Ceff / (2P)
TTFT ≈ Tqueue + Ttokenize + S / Rprefill + Tfirst-tokenS 为输入 token 数。长输入还要加入随 S² 增长的注意力项；排队经常比纯计算更主导 TTFT。

3.3 Decode：计算与访存两个上限

Rout,compute ≈ Ceff / (2P)
Rout,memory ≈ N × Beff / (W + N × DKV)
Rout ≤ min(Rout,compute, Rout,memory)N 为活跃序列数，DKV 为每序列每步 KV 等相关读取量。N=1 且 KV 可忽略时，退化为最常用的 B/W。
最常用的单流近似： output tok/s ≲ 显存带宽 ÷ 权重字节数。TP2 可先用两卡聚合显存带宽估算理想上限，再为 KV、PCIe TP 通信和运行时损耗留出余量；它不是通用公式。

3.4 MTP / 推测解码为什么能突破朴素 B/W

Rout,MTP ≈ E[accepted tokens + 1] / Tstep一次主模型验证可能推进多个 token，但会增加 draft/verify 计算。收益取决于接受率、每步推进数、输出长度和并发。

3.5 TPM、QPS 与输出吞吐的换算

Output TPM = 60 × output tok/s
Total TPM = 60 × (input tok/s + output tok/s)
QPS = Total TPM / [60 × (S + O)] = Output TPM / (60 × O)最后两个等式用于同一固定负载、同一测试轮次的记账换算；Total TPM 不同输入长度之间不可直接比较。

TP2 KV 容量是什么？

它是启动时为 KV Cache 预留的逻辑 token 槽位总数，不是当前使用量，也不是每请求容量。两卡分片存储 KV，但该数值已是 TP2 实例的逻辑容量，不能再乘以 2。

max-num-batched-tokens 是调度预算，不是总 KV 上限。

峰值功耗低，是否等于省电？

初步观察 NVFP4 峰值功耗低约 10%～15%，但峰值不等于平均能耗。只有在相同负载和 SLA 下比较稳态平均功耗与吞吐，才能判断能效。

07 / OPTIMIZATION PLAYBOOK

六类典型场景的优化思路

01

单流 / 低并发交互

目标：最低 TTFT 与 TPOT，而不是整机峰值。

  • 8K/512、MTP 关闭时，TP2 单流约 65.8 tok/s；MTP=3、并发 1 时聚合输出为 FP8 93.25、NVFP4 100.30 tok/s，NVFP4 TPOT 8.33ms 亦低于 FP8 的 8.95ms。
  • 开启 CUDA Graph，吞吐测试不要用 --enforce-eager。
  • 长输出可 A/B MTP，观察接受率与每步推进数。
  • 验收：TTFT、TPOT P50/P95、单流 output tok/s。
02

长输入 / Prefill 密集

目标：缩短 prefill，同时避免阻塞 decode。

  • 在 TP2 下扫描 max-num-batched-tokens；32768 是当前基线，下一步对比 16384。
  • 使用 chunked prefill，并控制入口长请求并发。
  • 共享前缀优先启用并验证 Prefix Cache 命中率。
  • 验收：按 2K/8K/32K 分层看 TTFT，不看混合均值。
03

高并发 / 短输出服务

目标：SLA 内请求 Goodput 最大。

  • max-num-seqs=32 是引擎调度上限，不是推荐入口并发。
  • MTP 关闭、8K/128 先限制入口为 8；MTP=3、8K/512 需区分聚合 SLA 点 20 与有效 TPM 点 8。
  • 8K/512 下，NVFP4 将聚合 SLA 最佳点推到并发 24，输出 tok/s 较 FP8 最佳点提升约 18.0%。
  • FP8 KV 可释放容量，但必须做业务质量回归。
  • 验收：原始 TPM、SLA 内 TPM、有效 TPM 三口径并列。
04

长输出 / Decode 密集

目标：降低 TPOT 与每输出 token 成本。

  • MTP 是重点 A/B 项，但不能外推固定 token 数。
  • 避免过大的 prefill budget 长时间干扰 decode。
  • 关注长上下文 KV 读取，而非只看权重 B/W。
  • 验收：512/2048 输出分别测试 TPOT、接受率与总成本。
05

Agent / 共享长前缀

目标：把重复 prefill 转化为缓存命中。

  • Prefix Cache 收益由共享比例与后缀长度共同决定。
  • 单 TP2 只有一个引擎和一份本地 Prefix Cache，重点检查前缀组织与命中率，不涉及跨实例路由。
  • 缓存命中不直接等于吞吐提升，还要观察 KV 容量、后缀长度和并发。
  • 验收：随机冷请求与共享前缀分组报告。
06

长上下文 / 显存受限

目标：不 OOM、不频繁抢占，并维持可接受 TPOT。

  • 先算权重、KV、激活与 runtime 的完整容量账。
  • TP2 的 FP8 KV 容量约 1.76×，32K 估算并发由 40.04 提至 70.59；本轮吞吐仅增约 3%～4%。
  • NVFP4 权重再节约 2.16 GiB/卡，使 MTP=3 对照下 KV 容量增加 3.81%；max-num-seqs=32 时仍先受调度上限约束。
  • 控制 max-model-len、并发与准入，监控 preemption。
  • 验收：32K 及目标最大上下文，补质量与尾延迟回归。
08 / CAPACITY & BENCHMARK

从理论估算走到生产容量

Roofline 用来判断数量级和瓶颈方向，真实负载压测用来确定运行点。两者之间不能跳过 SLA、请求分布与重复性验证。

第一步：理论边界

用参数量、精度、峰值算力、权重字节与显存带宽，分别计算 prefill/decode roofline；检查显存能否容纳权重和 KV。

第二步：负载矩阵

固定输入/输出长度扫描并发，再分别改变 batch、MTP、权重/KV 精度和 Prefix Cache，一次只改一个变量。

第三步：Goodput 与成本

以 SLA 过滤无效吞吐，选择有余量的膝点前运行点，并按 ECS 小时成本计算有效百万 token 成本。

Goodputrequest = 满足 SLA 的请求数 / 测试时长
Cost / 1M effective tokens = ECS 小时价格 / (有效 token/s × 3600 / 10⁶)“有效”必须同时绑定延迟和质量门槛；若按 token 统计 Goodput，应明确只统计哪些请求的哪些 token。

正确的心智模型

  • 理论吞吐 = 计算与访存 roofline 取小。
  • Prefill 通常偏计算，decode 低并发通常偏访存。
  • batch 能摊薄权重，却会增加 KV 与排队压力。
  • 优化必须绑定输入、输出、并发和 SLA。

需要避免的误区

  • 用 PCIe 128 GB/s 除以权重大小推 decode。
  • 把总 TPM 当 output TPM，或跨输入长度比较。
  • 把原始最大 TPM 当生产可承载容量。
  • 认为某个 batch、MTP 或拓扑永远最优。
最终结论： 对当前 27B FP8 单实例 TP2，理论计算上限约 117.8 万总 TPM；8K/128 冷请求聚合 SLA 内最佳约 38.8 万，出现在并发 8。NVFP4 在 8K/512、MTP=3 下将输出 tok/s 提升 7.6%～18.4%，SLA 可比点约 +18.0%；但业务质量与稳态能效仍需验证。
